# NEJE 2 BLE 통신 프로토콜 (NEJE 2 v2.5.6 APK 분석)

출처: `decompiled/sources/com/neje/Main/` — `MainActivity.java`, `neje/Command.java`, `ble/PictureSender.java`, `ble/CommandSender.java`

## 1. 연결

| 항목 | 값 |
|---|---|
| 광고 이름 | `Laser Carver` (구형 `Laser_Carver`는 이 프로토콜 미지원) |
| TX (앱→기기, Write) | 특성 UUID `0000FFE9-...` |
| RX (기기→앱, Notify) | 특성 UUID `0000FFEA-...` |
| MTU | 53 요청 → 실제 MTU = min(53, 협상값). 한 번에 보내는 데이터 = MTU-3 (보통 50바이트) |

연결 순서:
1. `connectGatt` → `discoverServices`
2. RX 특성의 CCCD 디스크립터에 `ENABLE_NOTIFICATION` 쓰기 + `setCharacteristicNotification(true)`
3. `requestMtu(53)`
4. `cmdVerify` 전송 → 기기가 **장치 정보(TYPE 1)** 로 응답하면 연결 완료
5. 이후 1초마다 `cmdRequestHeartBeat`, 각인 중에는 `cmdRequestProgress` 추가 전송

## 2. 프레임 형식 (양방향 공통)

```
FF AA LEN TYPE SUB/VER  ...payload...  55
```
- `LEN` = 헤더·꼬리를 포함한 **전체 바이트 수**
- 멀티바이트 정수는 **빅엔디언**
- 수신 측 파싱: `FF` 찾기 → 다음 바이트 `AA` 확인 → `LEN`만큼 모이면 마지막 바이트 `55` 확인

| 이름 | 바이트 (hex) | 설명 |
|---|---|---|
| Verify | `FF AA 08 01 01 5A A5 55` | 장치 정보 요청 (연결 확인) |
| Pause | `FF AA 08 02 01 01 00 55` | 일시정지 |
| Resume | `FF AA 08 02 01 01 01 55` | 재개 |
| Idle (중지) | `FF AA 08 02 01 01 02 55` | 작업 중지/대기 |

| HeartBeat | `FF AA 07 0B 01 00 55` | 온도/배터리 요청 |

| Battery(디버그) | `FF AA 07 00 01 07 55` | |

### 설정 (TYPE 3)
```
FF AA 0B 03 01 [carvingTime] [pwm] [weakLevel] [senseLevel] [fastMode] 55
```
| 필드 | 범위 (원본 UI) | 의미 |
|---|---|---|
| carvingTime | 0–100 | 각인 시간 (픽셀당 ms, UI 표시 "mS") |
| pwm | 1–100 | 레이저 파워 % |
| weakLevel | 0–100 | 약광(위치 표시용) 밝기 |
| senseLevel | 0–3 | 기울기 감지 민감도 |
| fastMode | 0/1 | 빠른/느린 모드 (지원 기기만) |

※ 5개 값을 항상 함께 보낸다. 연결 직후 기기가 보내는 TYPE 3 응답으로 현재 값을 받아 두고, 일부만 바꿔서 다시 보낸다.

### 위치 미리보기 (TYPE 5)
```
FF AA 10 05 01 'P'(50) [mode] [X:2] [Y:2] [W:2] [H:2] 55
```
- mode `02` = 미리보기 시작(약광으로 사각 테두리 표시), `00` = 미리보기 종료
- 좌표·크기 단위는 **기기 픽셀**

### 이미지 전송 (TYPE 4)
헤더:
```
FF AA 16 04 02 01 'P'(50) [X:2] [Y:2] [Wpad:2] [H:2] [dataLen:4] [W:2] 55
```
- `Wpad` = ceil(W/8)*8, `dataLen` = ceil(W/8) * H

전송 절차:
1. 헤더 전송
2. 기기 응답 `TYPE 4, SUB 2`: 값 `1`이면 전송 시작, 그 외는 "기기 사용 중"
3. 데이터를 (MTU-3)바이트씩 나눠 Write. 이전 Write 콜백(`onCharacteristicWrite`)을 받은 뒤 다음 조각 전송.
   원본은 속도를 약 **10,240 B/s**로 제한함 (조각 간격 = 조각크기×1000/10240 ms)
4. 기기 응답 `TYPE 4, SUB 4`: `1` = 성공, `0` = 실패

비트맵 인코딩 (1bpp, **검정 픽셀 = 1 = 각인**):
- 한 줄 바이트 수 `rb = ceil(W/8)`
- **짝수 줄(y%2==0)**: 정방향. 픽셀 x → byte `y*rb + x/8`, bit `0x80 >> (x%8)` (MSB 먼저)
- **홀수 줄**: 뒤집힌 방향(지그재그). 픽셀 x → byte `(y+1)*rb - x/8 - 1`, bit `1 << (x%8)`
  (= 해당 줄 전체를 비트 단위로 좌우 반전)

## 5. 새 앱 설계에 주는 의미

- 기기는 **흑백 1비트 비트맵 한 장 + 기기 좌표계의 오프셋(X,Y)** 만 받는다.
  → 이미지와 텍스트를 함께 배치하는 캔버스는 앱이 직접 합성한 뒤 비트맵 한 장으로 전송하면 된다.
- 좌표 단위는 기기 픽셀이며, `mmPerPixel`로 mm로 바꾼다 (예: 0.075mm/px).
- 사용자가 정한 "작업 구역"과 "영점(좌상/우상/좌하/우하)"은 **앱에서만 쓰는 개념**이다.
  앱이 사용자 좌표를 기기 좌표로 바꿔 오프셋을 계산한다.
  → 기기의 물리적 (0,0)이 어느 모서리인지는 실제 기기에서 미리보기(TYPE 5)로 확인해야 한다.
- 원본 앱의 이미지 변환: 그레이스케일(0.30R+0.59G+0.11B) → 임계값 128 이진화 또는 오차 확산 디더링.
- 원본 앱은 크기를 조절할 수 없고, 이미지가 항상 전체 영역에 맞춰 자동으로 커진다. 이 점이 개선 대상이다.
